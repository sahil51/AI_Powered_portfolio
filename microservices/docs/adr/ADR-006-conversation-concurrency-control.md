# ADR-006: Conversation Concurrency and State Locking

## Status
Proposed

## Context
PRD **Section 21 (Conversation State Machine)** defines a single-threaded state machine with linear transitions:
```
GREETING → INTENT_DETECT → NEEDS_TOOL → INFORMATION_COLLECTION → ...
```

However, the system is distributed (multiple FastAPI workers behind a load balancer). A user could send two rapid messages — both arrive at different workers simultaneously. Both workers would:
1. Read the same conversation state from Redis
2. Process each message independently
3. Write conflicting state back to Redis

This produces race conditions: lost messages, duplicate processing, corrupted state. The PRD does not address this.

## Decision
Implement **pessimistic locking** at the conversation level:

### Lock Mechanism
- Before processing any message, acquire a Redis distributed lock: `lock:conversation:{conversation_id}`
- Lock TTL: 30 seconds (should far exceed any single message processing)
- If lock cannot be acquired within 5 seconds, return HTTP 409 (Conflict) with retry-after header
- Lock released after state write completes

### Lock Acquisition Flow
```
1. Receive message for conversation_id
2. Try acquire lock `lock:conversation:{conversation_id}` (SET NX, TTL 30s)
3. If acquired → process message → write state → release lock
4. If not acquired → retry up to 3 times with 100ms backoff
5. If still locked → return 409 with Retry-After: 1
```

### Idempotency
- Each message carries an `X-Idempotency-Key` header (generated by frontend)
- Before processing, check Redis `idempotency:{key}` — if exists, return cached response
- Idempotency key TTL: 5 minutes
- This prevents double-processing even if the same message arrives at two workers

### Edge Cases
| Scenario | Handling |
|----------|----------|
| Worker crashes while holding lock | Lock auto-releases after 30s TTL |
| User sends message during meeting scheduling | Lock ensures sequential processing; second message is queued |
| Network partition causes lock timeout | Worker retries; if lock expired, it re-acquires |
| Same idempotency key from different conversations | Allowed — key is per-conversation |

## Consequences
- Maximum throughput per conversation: ~3 messages/second (limited by lock + processing)
- Multiple conversations processed in parallel without contention
- HTTP 409 is user-visible but rare (only under rapid-fire messages)
- Idempotency prevents duplicate booking even under race conditions
